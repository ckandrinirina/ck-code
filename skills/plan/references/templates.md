# Plan Skill — File Templates

Templates for files the `plan` skill writes (full mode and `--quick`). Substitute the
bracketed fields. `STORIES_INDEX.md` and `EPICS_INDEX.md` are **not** here — they are
generated by `ck-index` from frontmatter, gitignored, and never hand-written or committed
(see [`data-model.md`](../../../references/data-model.md)).

---

## Overview Template

Used for `OVERVIEW.md` at the root of every new plan folder (New Project and Increment
mode; Continue leaves the existing one untouched). The frontmatter is the **plan record**
([`data-model.md`](../../../references/data-model.md#plan-record-tasksplanoverviewmd)):
fill `slug` and `title`, leave the other five keys empty, then set the level with
`ck-plan set tasks/<plan> integration=<level>` (SKILL.md 5.2) — it also records
`branch: plan/<slug>` at level `plan`. `plan --publish --mode plan` writes `issue`,
`ship --promote` writes `pr`, and `ck-project sync` owns `delivery`. Keep the keys in
exactly this order. The body is prose; `ck-issues --mode plan` reads its `## Vision` and
`## Acceptance Criteria` for the plan issue.

```markdown
---
slug: [plan-slug]
title: [Plan Title]
integration:
branch:
issue:
pr:
delivery:
---

# [Plan Title]

## Vision

[One paragraph: what this plan delivers and the problem it solves. For an Increment,
also why now and what motivated it.]

## Architecture

[ASCII/text architecture diagram, derived from the spec or feature docs]

## Tech Stack

| Layer | Technology | Version |
| ----- | ---------- | ------- |
| ...   | ...        | ...     |

## Components

### [Component 1 Name]

- **Purpose:** [what it does]
- **Technology:** [stack]
- **Key responsibilities:** [list]

## Integration Points

[Increment only: existing components affected, new components introduced, and where the
new work meets the existing system. New Project: drop this section.]

## Key Design Decisions

- [Decision]: [rationale]

## Non-Functional Requirements

- **Performance:** [targets]
- **Security:** [considerations]
- **Compatibility:** [platforms/OS]

## Acceptance Criteria

- [ ] [Plan-level outcome a human can check]

## References

- Specification: [path to the spec or feature doc(s)]
- Generated: [date]
```

## Epic Template

Used for `epics/NN_<epic-slug>/EPIC.md`. Carries **frontmatter** and has **no
`## Stories` table** — the story list is generated into `STORIES_INDEX.md`. The generator
reads `description` for the `EPICS_INDEX.md` cell, and links the `Docs` cell when the
epic `slug` matches a `docs/architecture/features/<slug>/index.md`. **Set `slug:` to the
owning feature-doc dir name whenever one exists** (several epics may share one feature —
e.g. epics `03_keyboard-split-engine` and `04_keyboard-split-desktop` both get
`slug: keyboard-split`); an unlinked `Docs` cell strands builders without their
architecture doc. `title`/`description` must not contain `|` (table cells).
There is **no `integration:` key** — the level is the plan's, in `OVERVIEW.md`
([`branch-topology.md`](../../../references/branch-topology.md)). Leave `issue:`, `pr:` and
`delivery:` empty: `plan --publish` writes `issue`, `ship --promote` writes `pr` when it
opens the epic PR, and `ck-project sync` owns `delivery`. Keep `## Dependencies`: it
records *why* this epic waits on another, which `blocked_by` cannot.

```markdown
---
epic: NN
slug: [epic-slug]
title: [Epic Title]
description: [one-line goal — becomes the EPICS_INDEX Description cell]
issue:
pr:
delivery:
---

# Epic [NN]: [Epic Title]

## Description

[2-3 paragraphs: the epic scope, what it delivers, and why it matters]

## Goals

- [Goal 1]
- [Goal 2]

## Scope

### In Scope

- [Item]

### Out of Scope

- [Item]

## Dependencies

- **Depends on:** [prerequisite epics/stories, or "None"]
- **Blocks:** [epics/stories that depend on this]

## Acceptance Criteria

- [ ] [Criterion 1]
- [ ] [Criterion 2]

## Technical Notes

[Architectural decisions, patterns, or constraints specific to this epic]
```

## Story Template

Used for `epics/NN_<epic-slug>/stories/SS_<story-slug>.md` in **both** full and `--quick`
mode. The **frontmatter is the source of truth** for status, size, dependencies, and
touched files (see [`data-model.md`](../../../references/data-model.md)). Keep it
generator-readable: one `key: value` per line, inline `[…]` list values (or `[]`), no
block/multiline scalars. `status` lowercase, `size` uppercase `S`/`M`.

```markdown
---
id: [EE]-[SS]
title: [Story Title]
epic: [EE]
status: todo
size: [S|M]
blocked_by: [id, ...]
files: [path, ...]
issue:
pr:
delivery:
prior_status:
---

# Story [EE]-[SS]: [Story Title]

## Description

[Clear description of what this story implements and why]

## Acceptance Criteria

- [ ] [Criterion 1 — specific, testable]
- [ ] [Criterion 2]
- [ ] [Criterion N]

## Implementation Tasks

Ordered, concrete, verifiable steps one `build` session follows — specific to this story,
not generic TDD phases.

1. [ ] [Concrete step]
2. [ ] [Next step — continue until every acceptance criterion is satisfied]

## Technical Notes

[Implementation guidance, patterns to follow, algorithms, API contracts, data structures]
```

**Frontmatter notes:**

- `blocked_by` / `files` — inline flow `[a, b]` or empty `[]`. `files` lists the paths the
  story creates or modifies (the conflict-detection key); `[]` when unknown (`build` fills it).
- `issue:` / `prior_status:` — left empty by `plan`; `plan --publish` writes `issue`, `fix`/`build` manage `prior_status`.
- `pr:` / `delivery:` — the integration axis, also left empty by `plan`. `ship` writes both
  when it opens a PR; `ck-project sync` promotes `delivery` to `merged`. Never set them by
  hand ([`data-model.md`](../../../references/data-model.md#two-axes-status-is-work-delivery-is-integration)).
- `title` — no `Story EE-SS:` prefix (that lives in the body heading only).
