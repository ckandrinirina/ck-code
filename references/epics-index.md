# EPICS_INDEX.md — Generated View (Read Protocol + Selection Gate)

`tasks/EPICS_INDEX.md` is a **generated, read-only view**: one row per epic across all
plans, rolled up from story-file frontmatter by `scripts/ck-index.sh`. It sits above the
per-plan `STORIES_INDEX.md`: skills read it FIRST to see which epics exist and which are
unfinished, pick one, and only THEN drill into that epic's stories. It is never
hand-edited and never committed; `tasks/.gitignore` keeps it out of git, and it is
regenerated whenever it is missing or stale (see [`data-model.md`](data-model.md) for the
schema, the rollup rule and who regenerates the views).

See also: [`stories-index.md`](stories-index.md), the per-plan story view this sits above.

## Columns

```
| Epic | Plan | Status | Stories | Docs | Description |
```

| Column | Source |
|---|---|
| `Epic` | `NN · Name`, the number and the folder slug in title case |
| `Plan` | the plan folder under `tasks/` (informational) |
| `Status` | `TODO` \| `IN PROGRESS` \| `DONE` \| `MERGED`, computed |
| `Stories` | `done/total` over non-`skip` stories, computed |
| `Docs` | `docs/architecture/features/<slug>/index.md` when that feature doc exists (slug from `EPIC.md` `slug:`, else the folder slug), else `—` |
| `Description` | `EPIC.md` `description:` |

Each `epics/NN_<slug>/` in any plan is exactly one row, and `NN` is unique across every
plan ([`data-model.md`](data-model.md#epic-and-story-numbers-are-globally-unique)), so
the `Epic` cell identifies its epic on its own and the `Plan` cell is never needed to
disambiguate. `Status` and `Stories` are **computed** from that epic's story statuses
(never stored): `MERGED` when every non-`skip` story is `done` **and** `delivery: merged`
**or** `direct`; `DONE` when every non-`skip` story is `done` but at least one has not
reached the trunk; `IN PROGRESS` when any story is `in-progress`/`bug` or
some-but-not-all are `done`; `TODO` when none has started. A `bug` story counts as
not-done.

**`MERGED` and `DONE` are both finished.** `MERGED` is strictly stronger: it adds "and it
is all on the trunk branch". Nothing that looks for remaining work may treat a `MERGED` row
as unfinished; see the read protocol below.

## Read protocol

Before any phase that selects work (`build` Phase 1 / PARALLEL MODE P1):

1. Read `tasks/EPICS_INDEX.md`. If it is missing, lacks the `GENERATED by ck-code`
   header, or is older than any plan's `STORIES_INDEX.md`, regenerate: `ck-index`, then
   read it. (`ck-view` does this check itself.)
2. Parse the table as the authoritative epic list. Do NOT open any `STORIES_INDEX.md` yet.
3. Compute the **unfinished set** = rows whose `Status` is neither `DONE` **nor** `MERGED`.
   Both are finished states; counting `MERGED` as unfinished would re-offer completed,
   already-shipped epics for building.
4. Apply the **epic-selection gate** (below).
5. Only after an epic is chosen, read its `Plan` → `STORIES_INDEX.md`, filtered to that
   epic's `NN`, for story selection / parallel-safe / wave logic scoped to that epic.

## Epic-selection gate (build — inline and PARALLEL MODE)

Branch on the size of the unfinished set:

- **0 unfinished** → tell the user every epic is finished (`DONE` or `MERGED`); suggest
  `/ck-code:plan` to add work. Stop.
- **1 unfinished** → auto-select it (announce which); proceed to its story selection.
- **2 unfinished** → skip the epic prompt; fall through to the existing story-selection
  flow across both. The threshold for asking is **strictly more than two**.
- **> 2 unfinished (3+)** → **AskUserQuestion: "Which epic do you want to build?"**:
  list each unfinished epic as `NN · Name (Plan) — Status, done/total — Description`.
  Single-select; the choice scopes the run to that epic. A story-ID / `--epic` argument
  bypasses this gate: explicit scope is always respected, and a globally unique number
  resolves its own plan with nothing to ask.

## Mutation (there is none — regenerate)

Epic status/counts are computed by the generator from story frontmatter. To change them,
change a story's `status` with `ck-story set`, which regenerates the views. The `Docs`
cell is filled by the generator when `features/<slug>/index.md` exists. There is no
cell-edit protocol and no "recompute the rollup in-phase" obligation: the rollup is
regenerated, never stored, and a stale copy is replaced on the next read.

## Rules

- **Never hand-edit `EPICS_INDEX.md`**: change story frontmatter (and/or add the feature
  doc) and regenerate.
- **Never stage or commit `EPICS_INDEX.md`**: it is gitignored and disposable.
- **Never open a per-plan `STORIES_INDEX.md` before reading `EPICS_INDEX.md`** in selection.
- **Never treat `MERGED` as unfinished**: it is `DONE` plus "all of it is on the trunk branch".
- **Always ask which epic to build when more than two are unfinished**; with 0/1/2, never prompt.
