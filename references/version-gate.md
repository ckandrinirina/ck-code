# Version Gate — v3 Layout Enforcement (Shared Procedure)

Used by every **change-producing** ck-code skill to guarantee a project is on the
**v3 doc layout** before it reads or writes any architecture doc. ck-code v3 does
**not** read the pre-v3 layouts (flat `features/<slug>.md`, the retired layer docs,
or a `v1` feature-index) — this gate is what makes that safe.

The gate is a **HARD GATE**: a blocking step that runs before any doc read/write,
not a best-effort hint (except in read-only skills — see Scope).

## The layout constant

```
LAYOUT = v3
```

This is the layout-compatibility major the current ck-code expects. It is bumped
**only** when the doc layout itself breaks. A future v4 that changes the layout
updates this constant; routine `v3.x.y` minor/patch releases do not touch it.

## The stamp: `tasks/VERSION.md`

A one-file marker recording the layout version a project conforms to. Lets the
gate short-circuit without a filesystem scan every session.

```markdown
<!-- AUTO-GENERATED by ck-code. DO NOT EDIT BY HAND. -->

ck-code: 3.0.0
layout: v3
```

- `layout:` — the layout-compatibility major (compared against `LAYOUT`).
- `ck-code:` — the full running version, for information; restamped opportunistically.

Location: `tasks/VERSION.md`, sibling to `FEATURE_INDEX.md`.

## Procedure

### Tier 1 — fast path (the common case, one read)

**Tier 1 lives inline in each skill; this file is opened only when it misses.** A skill's
Phase 0 reads `tasks/VERSION.md` itself and proceeds on `layout: v3` — so a migrated
project never loads this reference at all. Skills therefore restate *only* this one check,
never the Tier-2 detection below.

1. Read `tasks/VERSION.md`.
2. If it exists AND its `layout:` value equals `LAYOUT` (`v3`) → **PASS**. Proceed
   immediately; do not scan the filesystem, do not read this file. (If the `ck-code:` line
   differs from the running version, optionally restamp that one line — cheap, never a
   migration.)
3. Missing or `layout:` ≠ `v3` → read this file and run Tier 2.

### Tier 2 — full detection (only when the stamp is missing or stale)

Runs only when `tasks/VERSION.md` is absent, or its `layout:` ≠ `LAYOUT`. One
filesystem probe — any single marker means the project is pre-v3:

```bash
# pre-v3 markers — any hit = old layout
grep -lq "Schema: v1" tasks/FEATURE_INDEX.md 2>/dev/null && echo OLD            # v1 feature-index
ls docs/architecture/features/*.md 2>/dev/null | grep -q . && echo OLD          # flat feature doc (a file, not a <slug>/ dir)
ls docs/architecture/{components,api-contracts,database-schema,data-flow}.md 2>/dev/null | grep -q . && echo OLD  # retired layer docs
```

- **No marker found** → the project is already v3-shaped (it just predates the
  stamp, or `tasks/` is empty / greenfield). Write `tasks/VERSION.md` (Stamp,
  below) and **PASS**.
- **A marker found** → **BLOCK** (below). Never stamp a project that still
  carries the old layout.

### BLOCK

Print exactly:

```
⛔ This project uses the pre-v3 doc layout.
   ck-code v3 doesn't read the old layout.
   Migrate with /ck-code:doc-optimizer upgrade  →  [Run it now? y/N]
```

Then ask the user (`y`/`N`):

- **y** → invoke `Skill({ skill: "ck-code:doc-optimizer", args: "upgrade" })`.
  `upgrade` writes the stamp as its final step. When it returns, **re-run this
  gate from Tier 1** (which now PASSes) and continue the original skill.
- **N** → stop the current skill. Do not read or write any doc. The stamp is left
  unwritten, so the next session re-detects.

## Stamp (writing `tasks/VERSION.md`)

Write the stamp only when the layout is confirmed clean v3 — i.e. after a Tier-2
"no marker found", or as the final step of `doc-optimizer upgrade`. Never before
migration. Create `tasks/` first if it does not exist (`mkdir -p tasks`) — on a
greenfield `design` run `tasks/` may not exist yet. Content: the template above with
`layout: v3` and `ck-code:` set to the running plugin version (from
`${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json`; if unavailable, write
`layout: v3` and omit the `ck-code:` line).

## Scope

| Skills                                                                                                             | Gate behavior                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `design`, `plan`, `pre-spec`, `quick-story`, `build`, `parallel-build`, `fix`, `sync`, `ship`, `to-issues`, `team` | **Hard-block** — run the full procedure; BLOCK halts the skill.                                                                                                                             |
| `explain`, `help`, `start`, `track`                                                                                | **Hint only** — run Tier 1 + Tier 2 detection, but on a marker emit one line (`ℹ pre-v3 doc layout — run /ck-code:doc-optimizer upgrade`) and continue read-only. Never block, never stamp. |
| `doc-optimizer`                                                                                                    | **Never gates** — it is the migrator. `upgrade` writes the stamp.                                                                                                                           |

A change-producing skill lists this gate in its **HARD GATES** block and links
here. It inlines the Tier-1 stamp check (above) so the common case costs one small
read; it never restates the Tier-2 detection logic.

## Rules

- **Never read or write an architecture doc before this gate PASSes** in a
  change-producing skill.
- **Never stamp `tasks/VERSION.md` while a pre-v3 marker is present** — stamp only
  after a clean detection or a successful `upgrade`.
- **Never auto-migrate without the `y` confirmation** — BLOCK always asks.
- **Compare on `layout:` (the major), never the full `ck-code:` version** — a
  minor/patch difference is not a migration trigger.
- **Tier 2 runs only on a missing/stale stamp** — a valid `layout: v3` stamp short-
  circuits with no filesystem scan and without loading this file.
