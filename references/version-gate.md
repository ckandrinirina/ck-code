# Version Gate — v7 Layout Enforcement (Shared Procedure)

Used by every **change-producing** ck-code skill to guarantee a project is on the
**v7 layout** before it reads or writes any project state. The layout is defined in
[`data-model.md`](data-model.md). In short: story frontmatter is the only source of truth,
each plan carries an `OVERVIEW.md` record, and the generated views are regenerated and
never committed.

v7 differs from v6 in four ways:

- **The views are out of git.** `STORIES_INDEX.md` and `EPICS_INDEX.md` sit behind
  `tasks/.gitignore` and are regenerated from frontmatter at every session start and
  on every read. v6 committed them, so each state flip needed a bookkeeping commit.
- **The stamp is stable.** `tasks/VERSION.md` no longer carries the running plugin
  version, which the session hook rewrote after every update and left the tree dirty.
- **Each plan has a record.** `tasks/<plan>/OVERVIEW.md` replaces `PROJECT_OVERVIEW.md` and
  `FEATURE_OVERVIEW.md`. Its frontmatter holds the plan's integration level, branch, PR
  and issue, which v6 scattered across every `EPIC.md`.
- **One word per concept.** A *feature* is an architecture doc and nothing else. What
  covers a whole plan is a *plan*: `integration: plan`, the `plan/<slug>` branch,
  `--mode plan`, and the `EPICS_INDEX.md` view with one row per epic.

The gate is a **HARD GATE**: a blocking step before any state read or write, except in
read-only skills (see Scope).

## The layout constants

```
LAYOUT = v7
MIN_PLUGIN = 7.0.0
```

`LAYOUT` is the layout-compatibility major the current ck-code expects. It is bumped
**only** when the layout itself breaks, independently of the plugin version.
`MIN_PLUGIN` is the first ck-code release that reads `LAYOUT`. It is written into the
stamp as `requires:`, so a clone opened with an older plugin is told to update, not to
migrate. Both change together, in the same release as the migration that produces the
new layout.

## The stamp: `tasks/VERSION.md`

```markdown
<!-- AUTO-GENERATED by ck-code. DO NOT EDIT BY HAND. -->

layout: v7
requires: ck-code >= 7.0.0
```

- `layout:` — compared against `LAYOUT`.
- `requires:` — the oldest plugin that can read this layout.

Nothing rewrites the stamp except a migration or the creation of a new project, so an
ordinary plugin update never touches a tracked file.

Location: `tasks/VERSION.md`.

### Both directions of mismatch

| Stamp says | Running plugin | Verdict |
|---|---|---|
| `layout:` older than `LAYOUT` | any | **BLOCK → migrate** |
| `layout:` newer than `LAYOUT` | older than the project | **BLOCK → update the plugin** — never migrate |
| `requires:` above the running version | older than the project | **BLOCK → update the plugin** |
| `layout:` == `LAYOUT` and `requires:` met | current | **PASS** |

A newer layout can never be converted down. Offering `migrate` there would rewrite a
teammate's project into a shape their own plugin no longer reads.

### The stamp is also what makes ck-code *required*

A project carrying this file keeps its plan, stories and architecture in a layout only
the plugin maintains. A clone of it on a machine with no ck-code has no command that can
read or write that state, and nothing in the plugin able to say so, because the plugin is
what is missing. The stamp therefore travels with a committed guard:

```bash
ck-bootstrap install
```

It writes `.claude/ck-code-required.sh` and wires it as the project's own `SessionStart`
hook in `.claude/settings.json`, which it also opts into the plugin. On a machine that has
ck-code the guard is silent. On one that does not, it stops the session and asks for
`/plugin install ck-code@ck-marketplace` before any work starts. Both files must be
**committed** to be worth anything. `ck-doctor` reports it when they are missing, stale,
gitignored or untracked.

## Procedure

### Tier 1 — fast path (the common case, zero reads)

**Tier 1 lives inline in each skill; this file is opened only when it misses.** Each
change-producing skill's Phase 0 carries the stamp as a `` !`…` `` dynamic-context
injection, so Claude Code runs the `cat` *before* the skill content is sent and the model
receives the stamp already rendered. Skills restate *only* this one check, never Tier 2.

```
Layout stamp: !`cat "$(git rev-parse --show-toplevel 2>/dev/null || pwd)/tasks/VERSION.md" 2>/dev/null || echo "ABSENT — no tasks/VERSION.md"`
```

1. Read the injected stamp. **Never spend a `Read` tool call on `tasks/VERSION.md`.**
2. `layout: v7` → **PASS**. Proceed with no scan and without loading this file. The
   session hook has already refused a `requires:` above the running plugin.
3. `ABSENT`, or any other `layout:` → read this file and run Tier 2.

The injection resolves from the **git repo root**, not the cwd, so a skill invoked from a
subdirectory still finds the stamp. Outside a git repo it falls back to the cwd.

### Tier 2 — full detection (only when the stamp is missing or stale)

One filesystem probe:

```bash
l=$(awk -F: '/^layout:/{gsub(/[ v\t]/,"",$2); print $2; exit}' tasks/VERSION.md 2>/dev/null)
[ -n "$l" ] && [ "$l" -gt 7 ] 2>/dev/null && echo NEWER                                      # a later ck-code wrote this
[ "$l" = 6 ] && echo V6                                                                       # v6 stamp
find tasks -mindepth 2 -maxdepth 2 \( -name PROJECT_OVERVIEW.md -o -name FEATURE_OVERVIEW.md \) 2>/dev/null | grep -q . && echo V6  # v6 plan record
git ls-files 'tasks/*STORIES_INDEX.md' tasks/FEATURE_INDEX.md 2>/dev/null | grep -q . && echo V6  # v6 committed views
find tasks -mindepth 3 -maxdepth 3 -type d -path 'tasks/*/epics/*' 2>/dev/null | sed 's|.*/epics/||;s|_.*||' | sort | uniq -d | grep -q . && echo LEGACY  # v5 colliding epic numbers
find .claude/skills/experts .claude/skills/guides -mindepth 2 -maxdepth 2 -name SKILL.md 2>/dev/null | grep -q . && echo LEGACY  # v4 nested team skills
find docs/architecture -maxdepth 2 \( -name DESIGN_LEDGER.md -o -path 'docs/architecture/features/*.md' \) 2>/dev/null | grep -q . && echo LEGACY  # v3 ledger, pre-v3 flat docs
find tasks -type f -path 'tasks/*/epics/*/stories/*.md' -exec grep -L '^id: ' {} + 2>/dev/null | grep -q . && echo LEGACY  # pre-v4 story
[ -f tasks/PLAN.md ] && echo LITE                                                             # ck-code-lite flat plan
```

- **`NEWER`** → BLOCK with the update message. Never offer `migrate`.
- **`V6`**, **`LEGACY`** or **`LITE`** → BLOCK with the migrate message. `migrate` detects
  which conversion applies. A legacy project is converted to v6 and then to v7 in the same
  run and the same commit.
- **No marker** → the project is v7-shaped or greenfield. Write the stamp (below) and
  **PASS**.

Every probe uses `find` or a plain test, never a `tasks/*/…` glob, because an unmatched
glob aborts the command under zsh. A `tasks/PLAN.md` is a lite plan, not an empty `tasks/`.

### BLOCK

For `NEWER`, print exactly, then stop the skill with no hand-off:

```
⛔ This project uses a newer ck-code layout than this plugin reads.
   Update the plugin: /plugin update ck-code@ck-marketplace — then restart.
   Never run /ck-code:migrate on it; a newer layout cannot be converted down.
```

For `V6`, `LEGACY` or `LITE`, print:

```
⛔ This project uses an older ck-code layout (v6 or earlier, or ck-code-lite).
   /ck-code:migrate converts it to v7 in one revertable commit.
   Migrate with /ck-code:migrate  →  [see the hand-off prompt below]
```

Then run the hand-off prompt from [`skill-invocation.md`](skill-invocation.md) for
`Skill({ skill: "ck-code:migrate" })`:

- **Run it** → `migrate` writes the stamp as its final step. When it returns, **re-run
  this gate from Tier 1** (it now PASSes) and **continue the original skill with its
  original arguments**. The user never retypes either command.
- **Run it, but the re-run still does not PASS** → `migrate` returned without stamping.
  Print the reason `migrate` gave and **stop the original skill**. Never re-offer the
  hand-off, and never call `migrate` a second time in the same run.
- **Skip** → stop the current skill. Do not read or write any project state.

## Stamp (writing `tasks/VERSION.md`)

Write only when the layout is confirmed v7: after a Tier-2 "no marker", or as the final
step of `migrate`. `mkdir -p tasks` first if absent. Run `ck-bootstrap install`
immediately after writing the stamp. The two belong together, and the SessionStart hook
only re-installs the guard on a project that already carries a stamp. Content is the
template above, with `layout:` = `LAYOUT` and `requires: ck-code >= <MIN_PLUGIN>`.

## Scope

| Skills | Gate behavior |
|---|---|
| `spec`, `design`, `team`, `plan` (incl. `--publish`), `build`, `fix`, `ship`, `config` | **Hard-block** — run the full procedure; BLOCK halts the skill. |
| `doctor --fix` | **Hard-block, DIRECTIVE** — doctor never calls `Skill` and never stamps. On anything but `layout: v7` (Tier 1, from the injected stamp) it prints the BLOCK message, then `NEXT: /ck-code:migrate` for an older or missing stamp (for `NEWER`, the update message alone — never migrate), and stops before any write. The read-only report (Phases 1–2) still runs first. |
| `ship` STANDALONE (no `tasks/` in the repo at all) | **Exempt** — a standalone commit on a never-planned repo touches no ck-code state. Skip the gate; never stamp. The moment `tasks/` exists, the hard-block row applies. |
| `explain`, `guide`, `track`, `doctor` (no `--fix`) | **Hint only** — Tier 1 alone, from the injected stamp. On anything but `layout: v7`, emit one line (`ℹ older ck-code layout — run /ck-code:migrate`, or `ℹ newer ck-code layout — update the plugin`) and continue read-only. Never run Tier 2, never block, never stamp. |
| `migrate` | **Never gates** — it is the migrator. It writes the stamp. It refuses a `NEWER` project. |

A change-producing skill lists this gate in its **HARD GATES** block and links here. It
inlines the Tier-1 stamp check and never restates Tier 2.

**Required Bash grants.** Every skill in the table above carries these in its
`allowed-tools`, whatever else it needs: `Bash(ck-bootstrap*) Bash(find*) Bash(grep*)
Bash(ls*) Bash(awk*) Bash(git ls-files*)`. The first is for the guard install that ships
with the stamp; the rest are for the Tier-2 probe.

## Rules

- **Never read or write project state before this gate PASSes** in a change-producing skill.
- **Never offer `migrate` for a `NEWER` layout** — update the plugin instead.
- **Always run `ck-bootstrap install` in the same step that writes the stamp.**
- **Never stamp `tasks/VERSION.md` while a `V6`, `LEGACY`, `LITE` or `NEWER` marker is present.**
- **Never auto-migrate without confirmation** — BLOCK always asks, per [`skill-invocation.md`](skill-invocation.md).
- **Never make the user retype the blocked command** — resume it once `migrate` returns.
- **Never write the running plugin version into the stamp** — it changed on every update and dirtied the tree. `requires:` changes only with the layout.
- **Tier 2 runs only on a missing or stale stamp** — a valid `layout: v7` stamp short-circuits.
