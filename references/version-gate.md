# Version Gate — v5 Layout Enforcement (Shared Procedure)

Used by every **change-producing** ck-code skill to guarantee a project is on the
**v5 layout** (story-frontmatter source of truth, generated indexes — see
[`data-model.md`](data-model.md) — plus **flat** team-skill folders) before it reads or
writes any project state. v5 does **not** read the v3 layout (prose `Status:` headers,
hand-maintained `Schema: v1/v2` indexes, `DESIGN_LEDGER.md`, flat/layer architecture
docs) — this gate is what makes that safe.

v5 differs from v4 in one artifact only: `/ck-code:team` writes
`.claude/skills/expert-<role>/SKILL.md` and `.claude/skills/guide-<tech>/SKILL.md`
instead of nesting them under `experts/` and `guides/`. Claude Code discovers project
skills at `.claude/skills/<skill-name>/SKILL.md` and takes the command name from that
directory, so the v4 nested folders were never registered as skills at all. Everything
else — stories, epics, architecture docs, indexes — is byte-identical to v4.

The gate is a **HARD GATE**: a blocking step before any state read/write (except in
read-only skills — see Scope).

## The layout constant

```
LAYOUT = v5
```

The layout-compatibility major the current ck-code expects. Bumped **only** when the
layout itself breaks — it is independent of the plugin version (a `5.x` plugin may speak
layout `v4` or `v5`). Routine releases do not touch it.

## The stamp: `tasks/VERSION.md`

```markdown
<!-- AUTO-GENERATED by ck-code. DO NOT EDIT BY HAND. -->

ck-code: <running plugin version, e.g. 5.6.0>
layout: v5
```

- `layout:` — compared against `LAYOUT`.
- `ck-code:` — the full running version, informational; restamped opportunistically.

Location: `tasks/VERSION.md`, sibling to `FEATURE_INDEX.md`.

## Procedure

### Tier 1 — fast path (the common case, one read)

**Tier 1 lives inline in each skill; this file is opened only when it misses.** A
skill's Phase 0 reads `tasks/VERSION.md` itself and proceeds on `layout: v5`. Skills
restate *only* this one check, never the Tier-2 detection.

1. Read `tasks/VERSION.md`.
2. Exists AND `layout:` == `LAYOUT` (`v5`) → **PASS**. Proceed; no scan, no loading
   this file. (If `ck-code:` differs from the running version, optionally restamp
   that one line.)
3. Missing or `layout:` ≠ `v5` → read this file and run Tier 2.

### Tier 2 — full detection (only when the stamp is missing or stale)

One filesystem probe — any single marker means the project is **not v5** (v4, v3 or
older, or a ck-code-lite project):

```bash
# pre-v5 markers — any hit = old layout, must migrate
ls .claude/skills/experts/*/SKILL.md .claude/skills/guides/*/SKILL.md 2>/dev/null | grep -q . && echo NESTED  # v4 nested team skills
ls docs/architecture/DESIGN_LEDGER.md 2>/dev/null | grep -q . && echo OLD                  # v3 design ledger
grep -lq "Schema: v1\|Schema: v2" tasks/*/STORIES_INDEX.md tasks/FEATURE_INDEX.md 2>/dev/null && echo OLD  # v3 hand-kept index
for f in tasks/*/epics/*/stories/*.md; do [ -e "$f" ] || continue; IFS= read -r l < "$f"; [ "$l" = "---" ] || { echo OLD; break; }; done  # a story without frontmatter = pre-v4
ls docs/architecture/features/*.md 2>/dev/null | grep -q . && echo OLD                     # pre-v3 flat feature doc
ls docs/architecture/{components,api-contracts,database-schema,data-flow}.md 2>/dev/null | grep -q . && echo OLD  # pre-v3 layer docs
ls tasks/PLAN.md 2>/dev/null | grep -q . && echo LITE                                      # ck-code-lite flat plan
```

The **`NESTED`** marker is the v4→v5 case and the only one that can fire on an otherwise
current project: the stories and docs are already right, but `/ck-code:team` wrote its
skills one directory too deep, where Claude Code never finds them. `migrate` renames the
folders, so the marker cannot re-fire afterwards. A v4 project on which `team` never ran
carries **no** marker — it is already v5-shaped and just re-stamps.

The **`LITE`** marker matters even though a lite project carries none of the `OLD` ones:
its `tasks/` holds a flat `PLAN.md` and no story files, so without this line the scan
finds nothing, stamps `layout: v5`, and ck-code plans straight past a plan it never read.
`migrate` renames `PLAN.md` on its way out, so the marker cannot re-fire afterwards.

- **No marker found** → the project is already v5-shaped (predates the stamp, or
  `tasks/` is empty/greenfield). Write `tasks/VERSION.md` (Stamp, below) and **PASS**.
- **A marker found** → **BLOCK**. Never stamp a project carrying an old, nested or lite layout.

### BLOCK

Print exactly — for a `NESTED` marker (and no `OLD`/`LITE`):

```
⛔ This project's team skills are nested (.claude/skills/experts/, guides/).
   Claude Code only finds skills at .claude/skills/<name>/SKILL.md, so none of
   them are registered — /ck-code:migrate flattens them to expert-*/ and guide-*/.
   Migrate with /ck-code:migrate  →  [Run it now? y/N]
```

For an `OLD` marker (it wins over `NESTED` — the full conversion covers both):

```
⛔ This project uses a pre-v4 layout.
   ck-code stores story state in frontmatter and generates its indexes.
   Migrate with /ck-code:migrate  →  [Run it now? y/N]
```

For a `LITE` marker:

```
⛔ This project uses the ck-code-lite layout (tasks/PLAN.md).
   ck-code needs epics, stories, and frontmatter — /ck-code:migrate converts it,
   keeping every task's status, acceptance criteria and history.
   Migrate with /ck-code:migrate  →  [Run it now? y/N]
```

Then ask (`y`/`N`):

- **y** → invoke `Skill({ skill: "ck-code:migrate" })`. `migrate` writes the stamp as
  its final step. When it returns, **re-run this gate from Tier 1** (now PASSes) and
  continue the original skill.
- **N** → stop the current skill. Do not read or write any project state. The stamp
  is left unwritten, so the next session re-detects.

## Stamp (writing `tasks/VERSION.md`)

Write only when the layout is confirmed clean v5 — after a Tier-2 "no marker found",
or as the final step of `migrate`. Never before migration. `mkdir -p tasks` first if
absent (greenfield `design`). Content: the template above with `layout: v5` and
`ck-code:` set to the running plugin version (from
`${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json`; if unavailable, write `layout: v5`
and omit the `ck-code:` line).

## Scope

| Skills | Gate behavior |
|---|---|
| `design`, `plan`, `build`, `fix`, `spec`, `ship` (incl. `--to-issues`), `team` | **Hard-block** — run the full procedure; BLOCK halts the skill. |
| `explain`, `guide`, `track` | **Hint only** — run Tier 1 + Tier 2, but on a marker emit one line (`ℹ pre-v5 layout — run /ck-code:migrate`) and continue read-only. Never block, never stamp. |
| `migrate` | **Never gates** — it is the migrator. It writes the stamp. |

A change-producing skill lists this gate in its **HARD GATES** block and links here.
It inlines the Tier-1 stamp check so the common case costs one small read; it never
restates the Tier-2 detection.

## Rules

- **Never read or write project state before this gate PASSes** in a change-producing skill.
- **Never stamp `tasks/VERSION.md` while a pre-v5, nested or lite marker is present** — stamp only after a clean detection or a successful `migrate`. A `tasks/PLAN.md` is a lite plan, not an empty `tasks/`.
- **Never auto-migrate without the `y` confirmation** — BLOCK always asks.
- **Compare on `layout:` (the major), never the full `ck-code:` version.**
- **Never treat a `NESTED`-only project as a full pre-v4 conversion** — its stories, epics and docs are already current; only the skill folders move.
- **Tier 2 runs only on a missing/stale stamp** — a valid `layout: v5` stamp short-circuits with no scan and without loading this file.
