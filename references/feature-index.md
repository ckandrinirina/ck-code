# FEATURE_INDEX.md — Shared Format & Protocol

A single, top-level rollup of every **feature** (= one epic) across **all** plan
folders. It sits one layer above the per-plan `STORIES_INDEX.md`: skills read it
FIRST to see which features exist and which are unfinished, pick one, and only
THEN drill into that feature's story rows. One feature-index read replaces
opening every plan's story index — that is the token saving it exists for.

See also: [`stories-index.md`](stories-index.md) — the per-plan, story-level index
this sits above.

## Location

`tasks/FEATURE_INDEX.md` — at the root of `tasks/`, sibling to the dated plan
folders. **One file for the whole project**, spanning every `tasks/<slug>/` plan.

## Definition: feature = epic

A **feature** is one epic. Each `epics/NN_<slug>/` in any plan folder is exactly
one row in this index. The index never descends to story level — that is the
job of `STORIES_INDEX.md`. The description is an epic-level, one-line summary —
"a mention", not implementation detail.

## Format (schema v1)

```markdown
# Feature Index

<!-- AUTO-GENERATED by ck-code (plan, build, parallel-build, fix). DO NOT EDIT BY HAND. -->
<!-- Schema: v1 -->

| Feature         | Plan                       | Status      | Stories | Description                                           |
| --------------- | -------------------------- | ----------- | ------- | ----------------------------------------------------- |
| 01 · Foundation | 2026-06-01_myapp           | DONE        | 3/3     | Server bootstrap, config loading, structured logging. |
| 02 · Auth       | 2026-06-01_myapp           | IN PROGRESS | 1/3     | Login form, session management, 2FA.                  |
| 03 · Billing    | 2026-06-10_feature-billing | TODO        | 0/4     | Subscription plans, Stripe integration, invoices.     |
```

Column rules:

- **Feature** — `NN · Display Name` (matches the epic folder `NN_slug` with `_` → `·`, title-cased). `NN` is the epic number _within its plan_.
- **Plan** — the `tasks/<slug>` folder name (without the `tasks/` prefix) the epic lives in. Locates that feature's `STORIES_INDEX.md` and `EPIC.md`.
- **Status** — rolled up from the epic's stories (see Status Rollup below): `TODO`, `IN PROGRESS`, or `DONE`.
- **Stories** — `<done>/<total>` story count for the epic (SKIP stories excluded from both numerator and denominator).
- **Description** — one-line epic summary; the `EPIC.md` "Goal"/first description line. Helps `fix` understand a feature without reading its stories.

Rows are sorted by `Plan` (oldest plan first), then by `Feature` number. Because
`NN` resets per plan, the `Plan` column is what disambiguates two epics that
share a number. The two HTML comments are mandatory — schema validation keys on
`Schema: v1`.

## Status Rollup

Derive each feature's `Status` from its stories in the matching `STORIES_INDEX.md`:

- **DONE** — every non-SKIP story in the epic is `DONE`.
- **IN PROGRESS** — at least one story is `IN PROGRESS`, OR some (but not all) non-SKIP stories are `DONE`.
- **TODO** — no story has started (all `TODO`, ignoring SKIP).

An epic whose every story is `SKIP` is `DONE` (nothing left to build).

## Read Protocol

Before any phase that selects work (`build` / `parallel-build` Phase 1):

1. Read `tasks/FEATURE_INDEX.md`.
2. If it exists AND contains `<!-- Schema: v1 -->` → parse the table as the authoritative feature list. Do NOT open any `STORIES_INDEX.md` yet.
3. If missing or schema mismatch → run **Bootstrap** (below), then re-read.
4. Compute the **unfinished set** = rows whose `Status` ≠ `DONE`.
5. **Feature-selection gate** (see below) decides whether to ask the user which feature to build.
6. Only AFTER a feature is chosen, read that feature's `Plan` → `STORIES_INDEX.md` and filter to the chosen epic's `NN` to get its ready stories. Now the normal story-selection / parallel-safe / wave logic runs, scoped to that one feature.

## Feature-Selection Gate (build & parallel-build)

After step 4, branch on the size of the unfinished set:

- **0 unfinished** → tell the user every feature is `DONE`; suggest `/ck-code:plan` to add a new feature. Stop.
- **1 unfinished** → auto-select it (announce which), skip the prompt, proceed to its story selection.
- **2 unfinished** → skip the feature prompt; proceed to the existing story-selection flow across both (the story menu already lets the user pick). The threshold for asking is **strictly more than two**.
- **> 2 unfinished (3+)** → **AskUserQuestion: "Which feature do you want to build?"** — list each unfinished feature as `NN · Name (Plan) — Status, done/total — Description`. Single-select. The chosen feature scopes the rest of the run to its epic. (A user-supplied story-ID / `--epic` argument bypasses this gate — explicit scope is always respected.)

## Bootstrap (creation when absent)

Fires when `tasks/FEATURE_INDEX.md` is missing or schema-incompatible. **Both
`build`/`parallel-build` and `plan` create it before any other action if it does
not exist** — the index must exist before work is selected.

1. `Glob "tasks/*/STORIES_INDEX.md"` — one row source per plan (bootstrap the story index first per [`stories-index.md`](stories-index.md) if any is itself missing).
2. For each plan, group its story rows by epic `NN`; for each epic compute `Status` (rollup) and `Stories` (`done/total`).
3. For each epic read its `EPIC.md` once to extract the one-line **Description** (Goal / first description line). This is the only multi-file read allowed here, mirroring the story-index bootstrap.
4. Sort rows by `Plan` then `Feature` number; write `FEATURE_INDEX.md` with the schema-v1 header and the table.
5. Tell the user: `Bootstrapped FEATURE_INDEX.md from N features across M plans.`

## Mutation Protocol

Keep the feature index in sync whenever epics or story statuses change. Update
the index in the SAME phase as the underlying change — never leave it stale.

| Skill                                                | When                                           | What changes in the index                                                                                                                                                                    |
| ---------------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `plan` (Phase 4)                                     | After writing epics + `STORIES_INDEX.md`       | Add one row per NEW epic (Status `TODO`, `0/N`, description from `EPIC.md`). Create the file first if absent. Continue/Add-Feature mode: insert the new rows, leave existing rows untouched. |
| `build` (Phase 1)                                    | After bootstrap/selection, before implementing | Backfill a blank/missing `Description` from the epic's `EPIC.md`; create the file if absent.                                                                                                 |
| `build` (Phase 8, on story DONE)                     | A story flips to `DONE`                        | Recompute the feature's `Stories` count and `Status` (→ `IN PROGRESS`, or → `DONE` when its last story completes).                                                                           |
| `build` (Phase 1.6, first story of a feature starts) | `TODO → IN PROGRESS` on the feature            | Status cell `TODO` → `IN PROGRESS`.                                                                                                                                                          |
| `parallel-build` (Phase 6, after each merge)         | Each merged story flips to `DONE`              | Recompute that feature's `Stories` count and `Status`; mark the feature `DONE` once its last story is merged.                                                                                |
| `fix` (stub story created)                           | A new stub story is added to an epic           | Recompute that feature's `Stories` total (and `Status` if it was `DONE`).                                                                                                                    |

Edit pattern (cell-only replacement — preserves table layout), e.g. on the last
story of a feature completing:

```
old: | 02 · Auth | 2026-06-01_myapp | IN PROGRESS | 2/3 | Login form, session management, 2FA. |
new: | 02 · Auth | 2026-06-01_myapp | DONE        | 3/3 | Login form, session management, 2FA. |
```

## Rules

- **Never** open a per-plan `STORIES_INDEX.md` before reading `FEATURE_INDEX.md` — the feature index is the first read in selection, and the whole point is to avoid opening every story index.
- **Always** create `FEATURE_INDEX.md` before any selection or planning action if it is missing — `build`, `parallel-build`, and `plan` each bootstrap it on demand.
- **Always** ask the user which feature to build when **more than two** features are unfinished; with 0/1/2 unfinished, never prompt (auto-select or fall through to story selection).
- **Never** descend below epic level in this index — one row per epic, descriptions are a one-line mention, not story detail.
- **Always** recompute a feature's `Status`/`Stories` rollup in the same phase a story under it changes status — after `build` and after each `parallel-build` merge, mark the feature `DONE` once its last story completes. Never leave the rollup stale after a completed build.
- **Never** edit the index by hand — the comment header is the contract; an explicit story-ID / `--epic` argument bypasses the feature-selection gate.
- A feature's `Description` is authored by `plan` and backfilled by `build`/`parallel-build` from `EPIC.md` when blank — it exists so `fix` has feature context without reading stories.
